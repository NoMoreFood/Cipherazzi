# Capture coverage and limitations

Cipherazzi records observable evidence and preserves unknowns. Capture depends on packets reaching a selected Packet Monitor component, supported framing, complete bounded reassembly, and the collector starting early enough to see the relevant exchange. A detected protocol or visible server selection does not establish successful authentication or tunnel completion.

## Network evidence

| Protocol / traffic | Observable evidence | Boundaries |
| --- | --- | --- |
| SSL 3.0, TLS 1.0–1.3 over TCP | Clear client/server hellos, offered and selected algorithms, visible extensions, supported public certificate and legacy key-exchange messages. STARTTLS inspection works on any port. | TLS 1.3 certificates, CertificateVerify, selected ALPN, and completion are encrypted. Capture can begin midstream or miss required packets. SSL 2.0 is unsupported. |
| QUIC v1/v2 | Initial hello evidence, Initial packet decryption using public protocol secrets, Retry handling, visible connection IDs, and association of paths using known IDs. | Handshake/application traffic is not decrypted. Encrypted connection-ID rotation, path validation, authentication, and completion remain unknown. |
| DTLS 1.0/1.2/1.3 | Cleartext hellos, cookies, and bounded handshake-fragment reassembly, with visible selections when present. | Encrypted records and encrypted authentication remain unavailable from passive capture. Application endpoint reports can supply DTLS completion and authentication metadata. |
| SSH 2.0 | Initial identification, KEXINIT offers, algorithm selection when endpoint roles are established, initial NEWKEYS activation, and supported visible server host-key metadata. | Host-key SHA-256 fingerprints are hexadecimal; captured keys and exchange signatures are not verified. Ordinary Ed25519, RSA, and named-curve ECDSA keys are supported for recognized exchanges. OpenSSH certificate-form host keys are inventoried with serial, key ID, principals, validity period, option names, and CA key fingerprint; their trust is reported as not verified. Speculative first-key-exchange packets are skipped rather than inventoried. Authentication and later encrypted rekey exchanges are unavailable. NEWKEYS does not establish user authentication. |
| WireGuard over UDP | Recognized handshake message formats and fixed protocol algorithm metadata. | Peer identity, successful authentication, tunnel completion, and encrypted application traffic are unavailable. |
| IKEv2 | Visible SA_INIT proposals and selections. | Encrypted authentication, established tunnel state, and ESP application traffic are unavailable. |
| OpenVPN over UDP or TCP | Clear control messages and reassembled control-channel TLS evidence, including bounded TCP length framing. | TCP inspection requires the initial clear reset and captured TCP roles. Changed session/key identifiers end inspection rather than combine exchanges. `tls-auth`, `tls-crypt`, encrypted data traffic, and authentication are not decrypted. |
| SMB 2.x/3.x over direct TCP or NetBIOS session framing | Negotiation dialects, signing flags, capabilities, SMB 3.1.1 encryption, signing, compression, and RDMA-transform context IDs, observed encrypted transform framing, compressed transform framing (decoded only for algorithms the host decompressor supports; no file payload is retained), SMB Direct negotiation limits and RDMA signing-transform descriptors when those transports are captured, and SESSION_SETUP evidence (see the SMB authentication row). | Capabilities are not proof that encryption or signing was used. Transform framing does not establish authenticity. Decrypted file operations are unsupported. Frames larger than 256 KiB exceed the inspection bound. |
| SMB1 NEGOTIATE over direct TCP or NetBIOS session framing | Offered dialect names, including the `SMB 2.002` / `SMB 2.???` hand-off to SMB2, the selected dialect index, the response layout (NT LM 0.12, LAN Manager, or core), and for NT LM 0.12 the server's signing enabled/required flags, challenge-response and extended-security indicators, and capability bits. | Only the NEGOTIATE exchange is decoded; session setup, authentication, per-message signing, and file operations are not. Signing flags are negotiated capabilities, not proof that traffic was signed. Server challenges, GUIDs, and times are not retained. The selected index is resolved to a dialect name only when the same connection's offer was captured; otherwise it is reported as sent. Pre-NT dialects carry no signing negotiation. A server that answers the hand-off with SMB2 is reported through the SMB2 fields. |
| RDP negotiation | Initial X.224 requested/selected security protocols or negotiation failure code, request/response flags, routing-cookie presence (the identifier is not retained), and correlation ID. For Standard RDP Security, the cleartext MCS Connect-Initial client encryption-method offers and the Connect-Response encryption method and level, with the server certificate type and RSA key size or X.509 chain length. Visible TLS evidence follows Enhanced security. | Server certificates are inventoried as key metadata only; signatures and chains are not verified. A reported Standard Security method is a negotiation outcome, not proof that the session was established or authenticated. Inspection ends at the MCS Connect-Response, so Standard Security key exchange and session traffic, CredSSP authentication, and encrypted sessions are not decoded. A capture that begins after the MCS exchange leaves only the X.224 evidence. |
| Kerberos over TCP or UDP | AS and TGS requests and replies and KRB-ERROR, recognized on any port by DER structure and, over TCP, the 4-byte length prefix: offered encryption types (including RC4 and DES), pre-authentication types and their encryption, ticket and reply encryption types, the service principal, the error code and name, and the encryption types a KDC lists in its pre-authentication or ETYPE-INFO errors. Change-password (kpasswd, RFC 3244) requests and replies: the operation implied by the protocol version, the AP-REQ ticket and authenticator encryption types and service principal, the AP-REP and KRB-PRIV encryption types, and for an unauthenticated failure the KRB-ERROR and its result code. | Only cleartext fields are read; tickets, authenticators, and encrypted parts are not decrypted or verified, so a reply does not establish successful authentication. The service principal is retained and `krbtgt/REALM` names the realm; client principals, request realms, salts, nonces, timestamps, and ticket contents are not retained. The new password, the principal it applies to, and the result of an authenticated change are inside KRB-PRIV, so a change-password reply does not establish that the password changed; version `0xff80` is reported as set or change because its target is encrypted, and result text is not retained. Each UDP datagram is a separate observation that is not paired with its request or reply. TCP messages over about 256 KiB exceed the inspection bound. A message is published only when it decodes completely. |
| SMB2 authentication in SESSION_SETUP | The SPNEGO mechanism list and selected mechanism, negotiation state, MIC presence, and the inner token: NTLMSSP NEGOTIATE/CHALLENGE/AUTHENTICATE flags and the target-information attributes offered, the NTLMv1/NTLMv2 and LM response form, whether a message integrity code or channel bindings were attached, anonymous authentication, and for Kerberos tokens the AP-REQ ticket and authenticator encryption types, the service principal, and mutual-authentication and user-to-user options. SMB session flags (guest, anonymous, encryption required) and the final session-setup status. | Evidence is read without verifying signatures, MICs, or responses, so it does not establish that authentication succeeded; the status and session flags report only what the server sent. Usernames, domains, workstation and server names, challenges, responses, session keys, and version fields are not retained. A security buffer that does not decode is recorded as undecoded and ends no other inspection. SMB1 session setup, NegoEx and IAKerb payloads beyond their mechanism OIDs, and encrypted SESSION_SETUP exchanges are not decoded. |
| TDS-wrapped TLS | Bounded PRELOGIN/response packet framing, a validated PRELOGIN option table (product version, encryption setting and client-certificate flag, MARS, federated authentication), TLS records spanning TDS packets, and transition to direct TLS. When both peers' PRELOGIN messages are captured with known roles, the protection their encryption settings negotiate: the entire session, the login only, none, or incompatible settings. A LOGIN7 packet sent outside TLS is reported as an unencrypted login. | TDS framing alone does not establish TLS. The negotiated protection follows the MS-TDS rules for the two settings as sent; it is not evidence that TLS completed, and it is not derived when roles are unknown or either PRELOGIN was missed. Login-only encryption leaves traffic after the login unencrypted. LOGIN7 contents are not read. SQL authentication and encrypted queries are not decoded. Inspection must observe the initial framing; malformed or unsupported framing ends inspection. |
| DTLS-SRTP | Client protection-profile IDs and visible DTLS 1.0/1.2 server selections; unknown profile IDs are retained. | DTLS 1.3 selection is encrypted and remains unavailable. Offers or selections do not establish media use, successful key establishment, or peer authentication. |
| Unidentified TCP/UDP with `--classify-raw` | Statistics and a possible-encryption classification for high-entropy samples of at least 4096 bytes. | Compression and random data can produce the same signal. Cipher, mode, key size, and successful encryption cannot be inferred from entropy. |

IPv4 and IPv6 fragmentation is supported when a complete, consistent datagram fits the reassembly limits. Conflicting or overlapping IP fragments are rejected. Missing fragments, timed-out assemblies, or exhausted limits leave incomplete evidence. DTLS handshake-fragment retransmissions must be consistent.

QUIC paths can be associated when a visible connection ID is already known. An address or port change by itself does not prove that unrelated packets belong to the same connection. Cipherazzi does not establish migration validation or decrypt newly issued connection IDs.

Encrypted Client Hello hides the inner server name. The visible outer name and an ECH-related extension are evidence only of what was visible; an extension can be GREASE and does not establish successful ECH negotiation.

## Endpoint evidence

Optional Schannel/CAPI2 events, Java Flight Recorder exports, and application reports can add public metadata unavailable on the wire. Availability depends on the provider, application, operating-system logging, and report fields. See [endpoint telemetry](EndpointTelemetry.md) for setup and contracts.

Application reports can state TLS, QUIC, or DTLS completion, peer verification, selected algorithms, handshake signature schemes, and public certificates. Successful DTLS reports use transport `DTLS` and the DTLS wire version (`0xfeff`, `0xfefd`, or `0xfefc`). Raw reports can state an application's encryption algorithm, mode, and key size. The collector correlates evidence using the process lifetime, socket identity, timing, and QUIC identifier where applicable, retaining provider provenance. A report is a trusted source's assertion; the collector does not independently prove its correctness or validate the endpoint's trust decision.

Java and Windows event providers do not necessarily emit every field required for full handshake authentication analysis. Installing Cipherazzi does not instrument every application's cryptographic implementation. Arbitrary encrypted traffic cannot reveal hidden algorithms or keys without appropriate endpoint evidence.

## Process ownership and capture sources

Local ownership combines process events and socket binding information. It is best effort: short-lived processes, protected processes, event loss, shared UDP bindings, and unavailable executable/account information can leave fields unknown. Remote process identity is generally unavailable. A PCAP does not contain the original local process ownership.

Default live sources are network interfaces plus same-host loopback. Use `--list-sources` to inspect the capture layers available on the target and `--source <id>` to select Packet Monitor components. A tunnel's outer packets and an inner application exchange have different visibility depending on the selected layer.

**Same-host (loopback) traffic** is captured by default with the packaged, signed WinDivert driver (the `CipherazziLoopback` directory beside the collector, installed by the MSI). It sniffs TCP and UDP copies and does not modify traffic. Built-in Packet Monitor alone can omit same-host connections, including localhost TLS. Use `--loopback-only` to capture only same-host traffic or `--no-loopback` to capture network sources without the driver; the two cannot be combined, and neither applies to replay or endpoint-only collection. The driver needs an elevated collector. If the package or driver cannot start, the collector reports an error that names `--no-loopback` instead of silently omitting same-host traffic. Loopback packets share the capture-health counters, and packets above the driver's maximum size are counted as truncated.

## Capacity and confidence

The collector bounds flow tracking, inspection storage, queues, IP/DTLS assemblies, and negotiation history. Default flow and inspection limits are 32,768 flows and 128 MiB. These are resource controls, not a guarantee that every connection will be admitted under every workload.

Packet Monitor streaming has a per-packet capture buffer limit of 9000 bytes in the collector. Oversized packet appearances, including some offload representations, can be dropped and counted as capture loss/truncation. Supported Packet Monitor offload representations are normalized during decoding; arbitrary oversized or unsupported framing is not guaranteed to be observable.

Inspect **Capture health** for losses, truncation, malformed input, unsupported capture layers, flow admission limits, reassembly limits, and process/endpoint source errors. Increasing inspection memory cannot recover packets already lost by Windows or enlarge the streaming packet-size limit. A TCP stream is searched for a TLS record, including one that follows STARTTLS, within the first mebibyte of each direction; a connection with no handshake in that span ends inspection without counting as a reassembly limit, while one that stops after a hello was seen is counted. Missing counters do not prove that uncaptured loopback or encrypted fields were observed.

Use completion, peer verification, algorithm classification, and certificate evidence independently. In particular:

- A client offer does not establish a server selection.
- A server selection does not establish handshake completion.
- A hybrid or post-quantum key exchange does not establish post-quantum authentication.
- A certificate's signature algorithm does not establish the encrypted handshake signature algorithm.
- A public certificate observed on the wire does not establish endpoint trust.
- A high-entropy payload does not identify an encryption algorithm.

## Verification boundaries

The 2026-10-07 SSH host-key, SMB, OpenVPN TCP, TDS/RDP, and DTLS-SRTP additions include native regression fixtures, but those fixtures have not been compiled or executed in this workspace: CMake Tools fails during configuration. Managed evidence-projection and general UI checks passed, as did the existing 46-check SQLite migration suite. These results do not validate the new native parsers; native build, fixture execution, and live interoperability checks are required before deployment. The available lab OpenSSL exposes DTLS 1.0/1.2 options, not DTLS 1.3.

The 2026-10-09 SMB1 NEGOTIATE parser has native regression fixtures (`smbLegacyCoverage` in `tests/Network.cpp`). They were run against `Framing.cpp` built outside the MSVC project, alongside the existing SMB2 and NetBIOS framing fixtures; the MSVC `Cipherazzi.Tests` build, the managed policy change that treats a selected SMB1 dialect as below any minimum, and live SMB1 interoperability remain unverified.

The 2026-10-09 RDP Standard Security parser has native regression fixtures (`rdpStandardCoverage` in `tests/Network.cpp`) built from recorded FreeRDP-to-xrdp exchanges: default, low, medium, FIPS, a 512-bit server key, negotiated Standard Security, and a TLS-only control. The recorded server responses were compared with an independent decoder, and the fixtures were run against `Framing.cpp` built outside the MSVC project; an RDP session now stays in framing mode until the MCS PDU arrives, which is a behavior change from finishing at the X.224 response. Windows RDP servers, other clients, the MSVC `Cipherazzi.Tests` build, and the viewer's display of the new fields remain unverified. The same-host capture description above follows the collector source and installer; `tests/LoopbackCapture.py` was not run for this revision.

Optional [syslog and Windows Event Log publishing](Publishing.md) exports selected committed snapshots and capture health. It retains the recorded evidence boundaries and can coalesce intermediate changes; enabling an output does not add capture or endpoint coverage.

The test tools cover deterministic protocol fixtures, actual endpoint exchanges, live VM capture, storage behavior, and UI workflows separately. DTLS 1.0/1.2 and IPv4 fragments have live lab checks. DTLS 1.3 and IPv6 fragment coverage currently rely on fixtures; they require additional live interoperability verification before making deployment-specific guarantees. QUIC path fixtures establish visible-ID association behavior, not encrypted migration validation.

Detection reports can include expectations that are unavailable from passive capture. Verify each expected field against its evidence source. A count of detected probes is not proof that every requested authentication or completion field was established. See [verification guidance](../tests/README.md) for running and interpreting checks.

The 2026-10-10 Kerberos, NTLMSSP, and SPNEGO parsers (`collector/Auth.cpp`) have native regression fixtures (`kerberosCoverage`, `smbAuthenticationCoverage`, and `authenticationEngineCoverage` in `tests/Network.cpp`). The Kerberos fixtures use recorded MIT Kerberos KDC exchanges and the SMB fixtures use recorded Samba session setups (NTLMSSP); the Kerberos-in-SMB2 fixture is synthesized from a builder because a recorded one could not be obtained. Parsers were compared with independent decoders, run whole, byte-at-a-time, and under random chunking, replayed through the engine, and exercised with 3,600 mutated streams under AddressSanitizer and UndefinedBehaviorSanitizer outside the MSVC project, with no findings. Windows KDCs and clients, other NTLM and SPNEGO stacks, the MSVC `Cipherazzi.Tests` build, `ctest`, and the viewer's display of the new fields (the managed edits were not built) remain unverified. The inspected SMB2 coverage row was refreshed from the collector source rather than re-tested.

The 2026-10-10 Kerberos change-password parser, Kerberos messages beyond 64 KiB, negotiated TDS encryption with unencrypted-login observation, and SMB1 dialect resolution have native regression fixtures (`kerberosPasswordCoverage`, the large-reply cases in `kerberosCoverage`, and the TDS and SMB1 outcome cases in `networkCoverage` and `smbLegacyCoverage` in `tests/Network.cpp`). No change-password, SQL Server, or SMB1 exchange was recorded: the fixtures follow the RFC 3244, MS-TDS, and SMB1 layouts, and the change-password request reuses the recorded MIT Kerberos AP-REQ. The MSVC `Cipherazzi.Tests` build and `ctest` passed, which also ran the earlier SMB1, RDP Standard Security, Kerberos, NTLMSSP, and SPNEGO fixtures named above; the protocol parser checks passed under AddressSanitizer, while the full suite under AddressSanitizer stops at an endpoint shutdown timing check outside these parsers. A capture written by a separate encoder ([NegotiationFixture.py](../tests/NegotiationFixture.py)) was replayed through the collector without capture-health errors and inspected with the viewer's `--protocol-ui --negotiation` check. MIT, Heimdal, Samba, and Windows change-password services, SQL Server and other TDS implementations, SMB1 servers, and live capture of these exchanges remain unverified.
